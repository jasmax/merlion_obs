From demo to production

Wiring it to the real agent

  1. Point the stack at the real data: MERLION_SOURCE=mysql with the same DB_* settings as the ingestion scripts (or Railway's MYSQL_URL). Tools and checks read the nine merlion_clean tables.
  2. Label the 90 real emails in golden/labels.json (python -m merlion_obs.dataset init). IDs and verdicts only, no personal data. Include the corporate-account emails: they are the refusal cases.
  3. Give the Spring tools the same span names and attributes (resolveOrder.query, getGpsTrail with gps.epoch_window, …) through Micrometer and OpenTelemetry, so these checks can run on the app's own Langfuse traces.
  4. Run python -m merlion_obs.evals --version vX in GitHub Actions. A non-zero exit blocks the merge; Railway's "Wait for CI" holds the deploy.
  5. Record the CS agent's final decision in feedback. Override rate is the one quality signal that needs no labels.
  6. python -m merlion_obs.otlp out/traces.db --push sends the traces to Langfuse Cloud. Check the weekly estimated spend there against the team budget.
